## Needs its own brainstorm

- **F-06-8, learning deadlines.** There is no due-date field anywhere in the learning model,
  so this is not a display fix. The design question is where the deadline lives. A single
  date on `Course` is simplest but wrong for a course assigned to several departments with
  different clinic calendars. A date on `CourseDepartment` fixes that but still cannot
  express "due two weeks after the volunteer is onboarded", which is what a rolling intake
  actually needs. A per-term assignment row would express all three but is a new table and a
  migration for existing progress. The choice also decides whether the reminder is a fixed
  date, a relative offset, or both, and whether an overdue course should escalate the
  onboarding step from blocking-with-no-date to something the schedule builder surfaces.
  Worth settling alongside the existing compliance and shift reminder cron, which already
  owns the "chase people about a deadline" job.

- **F-06-12, whether a course recurs per term.** Adding `termId` to `CourseProgress` is the
  easy half. The hard half is that "every course recurs each term" and "no course ever
  recurs" are both wrong, and the model currently cannot say which is which, so it silently
  applies the second to everything. Annual-refresh content (HIPAA-adjacent modules, patient
  safety) plainly should recur; a one-off orientation module plainly should not; and some
  will want "recurs yearly" rather than "recurs each term", which a per-term flag cannot
  express. The decision also has to cover what happens to a member mid-flight when an admin
  flips a live course from `ONCE` to `PER_TERM` (does an in-progress attempt reset, and does
  a currently-cleared volunteer become un-cleared), whether the reopened course should reuse
  the same `CourseProgress` row or start a new per-term one for audit purposes, and whether
  a recurring course needs a deadline, which folds straight back into F-06-8. Settle F-06-8
  and this together: they are the same missing per-term assignment concept seen from two
  sides.

## What worked well

Recorded so the fixes above do not accidentally undo it.

- **The quiz failure path is genuinely well built.** Failing produced a clear result card
  ("You scored 0%. You need 80% to pass. 2 attempts left. Review the highlighted answers and
  try again."), scrolled the learner back to the top to see it, moved focus to the score
  heading, and marked every question inline with a green "Correct" row and a red "Your
  answer" row. The attempt budget is visible before the first submit ("Pass at 80%, 3
  attempts left") and updates after each one. F-06-2 and F-06-3 are about what happens
  around this, not about the result card itself.
- **The zero-question guard already exists and reads well.** "Makeup quiz not ready yet /
  This training does not have any quiz questions yet. Please contact your coordinator so
  they can finish setting it up, then check back here." F-06-1 is asking for that exact card
  to also cover the unkeyed case, not for new copy.
- **The pre-window training notice explains itself.** "Your in-person training is on {date}.
  Attend the live session and your director marks you complete. Missed it? The makeup quiz
  opens {date}." That answers the three questions a volunteer would have. F-06-9 is only
  about getting them there without a dead-end click.
- **Progress in the SCORM player really does persist.** Completing a module, leaving via the
  header, and returning showed the course badge moved from "Not started" to "In progress"
  and the module still checked. F-06-6 is about saying so, not about fixing it.
- **The onboarding player correctly hides the app shell.** The gated course page renders in
  the onboarding chrome with no module nav, so none of the tabs that would eject the learner
  back to `/get-started` are on screen.
