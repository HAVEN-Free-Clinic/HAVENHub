## Coverage notes

- **Pure code read, no runtime verification.** No dev server or browser was used for this task,
  per its brief. Every row above is traced from source; where a finding depends on a state
  combination or rendered output I could not observe live, that is called out inline in the row.
- **`src/app/(app)/schedule/attendings/new/page.tsx` not read.** It almost certainly mirrors
  `[id]/page.tsx`'s edit form through the same shared `AttendingForm` component; given tier-2's
  lower depth and that the list and edit pages showed no findings worth filing, I judged a third
  near-duplicate CRUD page a poor use of the budget.
- **Sidebar/support components read only for the specific claim cited, not end to end:**
  `builder-grid.tsx` (only the `highlightDateKey` header-cell logic, for F-09-5),
  `pending-requests.tsx` (read in full, for F-09-1), `publication.ts` (only `publishSchedule`/
  `unpublishSchedule`, for F-09-6). `CapacityPanel`, `ReadinessPanel`, `AddPanelistForm`, and
  `BuilderCell` were not opened; the builder's RHD-specific "Readiness" column
  (`data.rhd != null`, `page.tsx:979-990`) is conditionally rendered per department, so its added
  complexity is invisible to directors outside RHD and I did not chase it further.
- **Recruitment pages outside the assigned list were not opened**: waitlist, subcommittees,
  the standalone `/training` tab, the interviews list, the applicants list, `builder/contract/*`,
  `builder/quiz/quiz-builder.tsx`, and the cycles list. I followed `cycle-nav.ts` far enough to
  confirm the Quiz tab exists and is reachable (load-bearing for not mis-filing F-09-2 as a
  missing-page problem instead of a missing-cross-link one), but did not read those pages' own
  content.
- **Schedule builder size verdict.** Requested by the brief: the builder (1,174-line page plus
  ~1,150 lines across `builder-grid.tsx`, `builder-cell.tsx`, `readiness-panel.tsx`,
  `capacity-panel.tsx`, and `pending-requests.tsx`) is mostly genuine complexity, not accumulated
  structure. It runs two views (Day/Grid) and two modes (assign/availability) over a real
  scheduling domain: per-role assignment, per-volunteer tags, availability tiers, capacity
  tracking, conflict badges, clearance banners, and a request-approval queue, none of which reads
  as redundant with another. Two things do look like accretion rather than necessity: (1) eleven
  near-identical `"use server"` action wrappers (`assignAction` through `denyRequestAction`,
  `page.tsx:290-516`) each re-deriving the same `base` redirect URL and calling `runAction` with
  the same shape, roughly 220 lines that a single parameterized helper could collapse without
  behavior change; (2) the RHD-only "Readiness"/attendings sub-feature is special-cased directly
  into the general builder page (`data.rhd != null` branches, plus the whole `attendings/` route
  tree) rather than living behind a cleaner extension point, though because it is conditionally
  rendered it costs non-RHD directors nothing in the UI itself -- it is a code-structure
  observation, not a filed UX finding.
- **No application code was changed.** `git status --short` was clean before this fragment was
  written and after, aside from this file.
